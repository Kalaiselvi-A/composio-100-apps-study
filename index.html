100 apps, one question:
can an agent use this?

Composio researches every app the same way before building a toolkit: what auth does it use, can a developer self-serve credentials, and how broad is the API. I ran that process across a real 100-app list, built the agent that did it, and checked its work by hand. 72 are self-serve buildable today. The other 28 aren't blocked by technology — they're blocked by who's allowed to ask.

01 — Patterns

The headline isn't the table. It's what clusters.

Insight over raw rows: three patterns held across all 100 apps, and they line up with where Composio would actually spend engineering time versus outreach time.

35 + 35

Auth is a coin flip, not a landslide

35 apps are API-key-only and 35 support OAuth2-or-key, almost dead even. Pure OAuth2-only shows up in 24 — mostly the big consumer/ads platforms (Meta, LinkedIn, Google Ads) where a key alone was never going to be enough anyway.

Dev tools & PM: 20/20

The safest category is the boring one

Every single Developer/Infra and Productivity/PM app in the list (GitHub, Notion, Linear, Stripe-adjacent infra, Supabase, Vercel...) is self-serve. Zero exceptions. That's the fastest 20 toolkits to ship.

9 of 10

AI/Research apps are the riskiest category

9 of the 10 "AI, Research & Media" apps are gated, partial, or blocked — plan-gated APIs (Otter, Grain, Fathom), sales-only data products (PitchBook), or consumer tools with no public API at all (Consensus, NotebookLM standalone). The category most associated with "agent-native" is, ironically, the hardest to actually wire an agent into today.

03 — The Agent

What did the research, and where a human stepped in

"Build an agent, not by hand" — here's the loop, what it does unattended, and the three places a human is still the better tool for the job.

01

Ingest

Read the assignment's 100-row app table into {name, hint} pairs — the exact schema the model has to fill in per app.

02

Research

One Claude Messages API call per app, web_search tool enabled server-side, forced into a strict JSON schema — auth, access, API surface, MCP status, verdict, blocker, evidence URL.

03

Verify

A stratified 21-app sample re-researched independently, live against docs, diffed field-by-field against the first pass. Errors logged, not hidden.

04

Cluster

patterns.py — pure analysis, zero API calls — turns the 100 rows into the aggregate findings shown in section 01.

# agent/research_agent.py — the actual loop, trimmed
payload = {
  "model": "claude-sonnet-4-6",
  "tools": [{"type": "web_search_20250305", "name": "web_search"}],
  "messages": [{"role": "user", "content": SCHEMA_PROMPT.format(name=name, hint=hint)}],
}
# -> POST to api.anthropic.com, parse the JSON object out of the final text block
Where a human was needed — three places, honestly: (1) judging whether a "gated" app is worth a partnership push or a dead end (Gladly vs. Brex read very differently to a sales team even though both scored "blocked/friction"); (2) catching a mid-research rebrand the model's training data wouldn't know about (FanBasis → Commas); (3) deciding when "no public API found" means defunct (iPayX) versus just not developer-facing yet (Consensus) — the agent can surface the ambiguity, but that call is a judgment call.

05 — Honesty notes

What defeated the agent, stated plainly

iPayX — the named company was acquired by BillingTree in 2017; no independent public API exists today. Likely a stale hint in the source list, flagged rather than invented.

Paygent Connect — no public API reference locatable at all. Marked "blocked / needs human check," which the assignment brief itself says is the correct honest finding, not a failure.

Sherlock & Mermaid CLI — not APIs. Local CLI tools. Toolkit-shaping either one means sandboxing a process, not calling a service — a different engineering problem than the other 98 rows.

79 of 100 rows — single-pass, good-faith, not independently hand-verified. See section 04 for exactly which 21 were.
